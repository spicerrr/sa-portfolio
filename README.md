Портфолио системного аналитика с фокусом на **цифровые продукты, интеграции и данные**.

Коммерческий опыт связан со сложными учётными контурами и цифровизацией внутренних сервисов. Здесь он разложен на переносимые инженерные навыки: **контракты API, модели данных, интеграционные сценарии, состояния, обработка ошибок и проверяемые требования**.

<a id="case-1"></a>

## 01 · Integration & Master Data Platform

> **Техническая реконструкция на основе коммерческого контекста.** Предметная проблема и типы данных основаны на рабочем опыте; опубликованная архитектура, контракты и примеры обезличены и не являются внутренней документацией компании.

### задача

Несколько систем описывают один физический объект разными локальными кодами и документами. Простое сопоставление по названию или дате приводит к дублям, неоднозначным связям и расхождениям между производственным и складским фактами.

### решение

| Уровень | Что спроектировано |
|:---|:---|
| **Master Data** | единый идентификатор сущности, соответствия локальных кодов, обработка неизвестных и конфликтующих значений |
| **REST API** | регистрация и чтение производственных фактов, разрешение справочных кодов, ошибки и идемпотентные повторы |
| **Событийный обмен** | JSON Schema для событий, RabbitMQ, повторная доставка, DLQ, outbox / inbox, идентификатор корреляции |
| **Данные** | PostgreSQL, целевая ERD, ограничения целостности, SQL для схемы и отчётной витрины |
| **Legacy migration** | промежуточный слой, нормализация, проверка дублей и конфликтов, сохранение происхождения исходной записи |
| **Проверка** | критерии приёмки, отрицательные сценарии и автоматическая проверка согласованности спецификаций |

## 02 · FitnessTech Mobile App

> **Продуктовый B2C-кейс.** Границы и архитектурная постановка определены; публичные спецификации будут добавляться только после согласования между собой API, состояния, данные и сценарии проверки.

### продуктовый контур

Мобильное приложение фитнес-сервиса с подпиской и несколькими связанными пользовательскими сценариями:

| Контур | Что входит в проектирование |
|:---|:---|
| **Подписка** | оформление, продление, заморозка, отмена, права пользователя и переходы между состояниями |
| **Эквайринг** | создание платежа, подтверждение, 3-D Secure / дополнительное действие, webhooks, повторные запросы и восстановление после сбоя |
| **Mobile API** | клиентские запросы, BFF / backend-контракты, ошибки, идемпотентность и согласованность статусов |
| **Push-уведомления** | события для напоминаний и сервисных уведомлений, предпочтения пользователя, повторная отправка |
| **Продуктовые события** | начало / завершение сценария, ошибки, конверсии, повторные действия пользователя |
| **Событийные интеграции** | Kafka-концепции, JSON Events, асинхронное обновление зависимых контуров |
| **B2C-сценарии** | основной поток, альтернативы, пограничные случаи, восстановление после ошибок сети и повторного действия пользователя |

### план артефактов

`requirements` → `State Machine` → `Sequence` → `ERD` → `OpenAPI` → `event contracts` → `acceptance criteria`

Для этого кейса не публикую пустые ссылки: он появится отдельным каталогом / репозиторием после появления проверяемого набора артефактов.
