## 01 · коммерческий опыт

**«Агроном-Сад» / цифровая трансформация**

| Зона | Что делала |
|:---|:---|
| **Внутренний продукт** | Разбирала ручные и Excel-процессы, собирала AS-IS / TO-BE и переводила их в требования к системе (роли, шаги, данные, проверки) |
| **ERP / WMS / TMS** | Описывала стыки между производством, складом и логистикой: где рождаются данные, кто ими владеет, куда они уходят и когда должны синхронизироваться |
| **Master Data** | Приводила к общей модели справочники сортов, участков, партий и операций: атрибуты, идентификаторы, дубли, mappings между источниками |
| **Интеграции** | Фиксировала состав обмена, источник / получателя, JSON / XML, контрольные точки, ошибки и повторную обработку |
| **Модели** | ERD для предметной области, UML для состояний / взаимодействий, BPMN для процессов и ручных разрывов |
| **BI / отчётность** | Формализовала требования к данным и витринам; отдельный кусок — ТЗ на дашборд «Паспорт сорта» |
| **Версионирование** | Git для технических артефактов: OpenAPI, PlantUML, SQL, mappings и служебные скрипты; feature-ветки → merge request → review → merge, теги для согласованных версий |

<details>
<summary><b>🏗 контур ЦТ</b></summary>
<br>

Для портфолио внутренний контур обезличен и собран как техническая реконструкция предметной области — без корпоративной документации и реальных идентификаторов.

**Production Management** — производственный учёт: участки, сорта, операции, факт работ, сбор урожая.  
**ERP** — ресурсы, экономика и документы.  
**WMS** — партии, ячейки, остатки и перемещения.  
**TMS** — рейсы, транспорт и статусы доставки.  
**MDM** — канонические справочники и mappings между системами.  
**BI / DWH** — урожайность, качество, затраты и логистика.

Обычная цепочка выглядит примерно так:

`Production → WMS → ERP → BI`

Партия создаётся в производственном контуре, принимается на складе, становится объектом учёта в ERP и дальше попадает в аналитику. Основная сложность — не сама передача полей, а ownership данных, единые ID и расхождения между источниками.

**Интеграционный слой в реконструкции:**
- REST / OpenAPI — синхронные запросы;
- RabbitMQ — события между контурами (например, `harvest.batch.created`, `warehouse.lot.received`, `shipment.status.changed`);
- retry / DLQ и идемпотентная обработка — для повторной доставки;
- PostgreSQL — операционные данные внутреннего продукта.

**Git / GitLab:** OpenAPI-контракты, PlantUML, SQL, mappings и служебные скрипты версионируются вместе с изменениями системы. Рабочая схема — короткая feature-ветка → MR → review → merge; согласованные срезы помечаются тегами.
