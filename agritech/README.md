## Задача бизнеса

Предприятие выращивает яблоки. Сбор учитывается по участку, сорту и сезону, после чего продукция поступает на склад. Руководителю нужны сопоставимые показатели: сколько собрано, сколько принято, какова урожайность сорта и какие партии требуют сверки.

Данные возникают в разных местах. Производство ведёт журнал сбора, склад — документы приёмки, агрономическая служба — сведения о посадках и площади. ERP хранит учётную номенклатуру и затраты, WMS — складские документы. У источников собственные коды и названия сортов.

Из-за этого подготовка отчёта требует ручной работы: определить, какой сорт обозначен в каждой записи, найти соответствующий документ приёмки и проверить единицы измерения. Несвязанные записи и повторные выгрузки искажают итог, если объединять их только по названию или дате.

**Граница кейса:** справочник сортов, регистрация сбора, одна полная приёмка партии и показатели «Паспорта сорта». Перевозки, разделение и смешение партий, частичная приёмка и распределение затрат описываются отдельными задачами.

<a id="solution"></a>

## Как задача разобрана в требованиях

### 1. Установить, какие данные уже существуют

В исходной модели сохранены реестр посадок, локальные справочники, строки документов сбора и приёмки. Для каждой записи определены её смысл, ключ и способ связи с остальными источниками.

![Исходная модель данных: документы и локальные связи](diagrams/rendered/as-is-data.svg)

[Полное описание исходной модели](docs/data-model.md#source-data) · [Исходник UML](diagrams/as-is-data.puml)

### 2. Разделить идентификаторы и измерения

Сорт, партия сбора и складской документ — разные объекты. Единый код сорта связывает справочники, номер партии связывает сбор с приёмкой, а исходные номера документов сохраняют происхождение данных.

В контрольном примере производство зарегистрировало **8420 кг**, склад принял **8370 кг**. В требованиях закреплено хранение двух измерений и разницы **−50 кг**. Изменять производственную массу по складскому значению нельзя. Если подтверждение ещё не получено, партия показывается отдельно как ожидающая данных о приёмке.

### 3. Описать действия участников и ответы системы

Оператор регистрирует сбор по исходному документу. Система проверяет участок, сезон, сорт и массу, выдаёт номер партии и передаёт реквизиты складу. Кладовщик связывает приёмку с этой партией и подтверждает собственное измерение. Отчёт объединяет связанные факты.

В сценариях отдельно разобраны неизвестный сорт, повтор документа, потеря ответа на регистрацию, недоступность склада и расхождение масс. [Пять сценариев использования и UML](docs/use-cases.md).

### 4. Задать проверяемый результат

| Требование | Как проверяется |
|:---|:---|
| Повтор запроса не создаёт вторую партию | После потери ответа повторить запрос и проверить прежний номер партии и количество записей |
| Приёмка не меняет массу сбора | Передать 8370 кг для сбора 8420 кг и проверить оба значения |
| Площадь не умножается на число сборов | Для нескольких партий с одних участков сравнить урожайность с ручным расчётом |
| Неполные сведения не превращаются в «потери» | Оставить часть партий без приёмки и проверить отдельное отображение таких партий |

[Полный план приёмки](docs/acceptance.md) содержит условия, действия, ожидаемые результаты и ссылки на требования.

## Проверка материалов

Автоматические проверки контролируют структуру OpenAPI и сообщений, примеры данных, ссылки, наличие диаграмм и покрытие требований сценариями приёмки.

```bash
python -m pip install -r agritech/requirements-check.txt
python agritech/scripts/validate.py
python agritech/scripts/normalize.py
python agritech/scripts/check_legacy.py
```

Результаты испытаний реализации фиксируются по [плану приёмки](docs/acceptance.md). Для проверки запросов подготовлена коллекция Postman.
