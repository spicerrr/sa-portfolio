# ✅ проверка требований

Ниже описаны сценарии, по которым проверяется реализация. В каждом указаны подготовка, действие и ожидаемый результат. Это план приёмки; результат выполнения на стенде фиксируется отдельно.

## Справочники и регистрация сбора

| ID | Подготовка и действие | Ожидаемый результат | Требования |
|:---|:---|:---|:---|
| AC-01 | В справочнике складской код сорта `WMS-V-22` связан с единым кодом `VAR-017`. Запросить сорт по этому складскому коду. Затем повторить запрос с неизвестным кодом. | Первый запрос возвращает `200` и `VAR-017`. Второй возвращает `404 MAPPING_NOT_FOUND`; новый сорт автоматически не создаётся. | BR-01, FR-01 |
| AC-02 | Участок `PLOT-044` в сезоне 2026 связан с сортом `VAR-017`. Отправить регистрацию сбора с этого участка, указав `VAR-099`. | Ответ `422 INVALID_REFERENCE`. Партия и исходящее сообщение не создаются. | FR-01, CON-01 |
| AC-03 | Подготовить два запроса по одной строке документа сбора, но с разными ключами запроса. Отправить их одновременно. | Один запрос возвращает `201`, второй — `409 SOURCE_RECORD_EXISTS`. В БД одна партия. | BR-02, FR-02 |
| AC-04 | Успешно зарегистрировать сбор и прервать получение ответа клиентом. Повторить запрос с тем же ключом и содержимым, изменив порядок полей JSON. | Возвращаются исходные `201`, номер партии и тело ответа. Второго исходящего сообщения нет. | FR-02 |
| AC-05 | Зарегистрировать сбор. Повторить запрос с прежним ключом, изменив массу. | Ответ `409 IDEMPOTENCY_CONFLICT`. Сохранённая масса не меняется. | FR-02 |
| AC-06 | При регистрации вызвать сбой сохранения до завершения транзакции. Затем повторить запрос. | После сбоя нет ни партии, ни исходящего сообщения. Повтор может создать одну партию. | FR-03 |
| AC-13 | Выполнить регистрацию без токена доступа, с токеном с неверной подписью и от имени пользователя без права регистрации. | Ответы соответственно `401`, `401` и `403`. Записей о сборе нет. | NFR-02 |
| AC-18 | Поочерёдно отправить нулевую массу, отрицательную массу, будущую дату и сезон, не совпадающий с годом сбора. Отдельно передать поле неверного формата. | Для недопустимых значений — `422 INVALID_BUSINESS_VALUE`; для нарушения формата — `400`. Партия не создаётся. | FR-01 |
| AC-19 | Подготовить соответствие нового локального кода сорту. Затем попытаться связать уже утверждённый код с другим сортом. | Первый выпуск содержит автора, основание и согласование владельца. Переназначение существующего кода блокируется до проверки связанных исторических записей. | BR-01, FR-06 |

## Передача данных и складская приёмка

| ID | Подготовка и действие | Ожидаемый результат | Требования |
|:---|:---|:---|:---|
| AC-07 | Отключить WMS на 30 минут. В это время зарегистрировать несколько сборов. Восстановить WMS и обработать накопленные сообщения. | Сборы регистрируются во время отключения. После восстановления для каждой партии появляется одна ожидаемая приёмка. | FR-03, NFR-01 |
| AC-08 | После подтверждения RabbitMQ прервать отправителя до отметки публикации в БД. Перезапустить отправителя. | Он может отправить сообщение повторно с тем же номером. В WMS вторая ожидаемая приёмка не создаётся. | FR-03, NFR-01 |
| AC-09 | Для партии с массой сбора 8420 кг передать подтверждение приёмки 8370 кг. Доставить то же сообщение повторно. | Одна приёмка с массой 8370 кг; сбор остаётся 8420 кг. Разница — минус 50 кг. | BR-03, FR-04 |
| AC-10 | Прервать получателя после сохранения складских сведений, но до подтверждения обработки сообщения. Возобновить получение. | Повтор распознан по журналу обработанных сообщений. Вторая запись не создаётся. | FR-04, NFR-01 |
| AC-14 | Зарегистрировать сбор и подтвердить приёмку. Проследить пользовательский запрос и оба сообщения в журнале. | У всех действий один `correlationId`. По нему можно восстановить цепочку; токен доступа в журнале отсутствует. | NFR-03 |
| AC-16 | В BI сначала доставить подтверждение приёмки, затем регистрацию сбора той же партии. | Подтверждение сохраняется до получения сбора, затем связывается с ним. Складские данные не теряются. | FR-04, NFR-01 |
| AC-17 | Вызвать временную ошибку получателя и сохранить её во время трёх повторных попыток. | Сообщение попадает в очередь ошибок с номером, причиной и числом попыток. Исходное сообщение подтверждается только после успешного переноса. | FR-03, NFR-01 |

## Как фиксируется результат

Для каждого сценария указываются версия требований и API, тестовые данные, ожидаемый и фактический результат, подтверждение из ответа, БД или журнала и номер дефекта. В проверках повторного запроса дополнительно подсчитываются созданные записи: успешный ответ сам по себе не доказывает отсутствие дублей.

Перед внедрением измеряются доля ручных сопоставлений, число неразрешённых кодов, доля партий без подтверждения приёмки и задержка передачи. Эти исходные значения используются для сравнения после внедрения.
