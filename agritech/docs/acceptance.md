# План приёмки и проверка модели

[← Данные и расчёты](data-model.md) · [К кейсу](../README.md)

Проверки сгруппированы по рабочим задачам: регистрация сбора, обмен со складом и отчётность. Для каждого сценария заданы исходные условия, действия и наблюдаемый результат. Идентификаторы BR, FR и NFR отсылают к [каталогу требований](requirements.md).

## Выполненная проверка SQL-модели

**Дата:** 14 октября 2026 года. **Среда:** PostgreSQL 18.6 в PGlite 0.5.9. Выполнены опубликованные файлы схемы, представления, контрольного набора и SQL-проверок. Проверки работают с результатом SQL-запроса и ограничениями БД.

| Проверка | Результат |
|:---|:---|
| Показатели исходного набора | Пройдено |
| Без подтверждения — 6,580 т | Пройдено |
| Площадь не повторяется по числу сборов | Пройдено |

[Результат расчёта исходного набора — CSV](../examples/passport-result.csv): площадь 5 га, сбор 15 т, урожайность 3 т/га, полученная приёмка 8,370 т, полнота 1/3, разница связанной пары −0,050 т.

Контрольные записи добавлены для проверки правил и не содержат производственных данных. Дополнительные случаи из `04_checks.sql` выполняются внутри транзакции с откатом; исходный контрольный набор сохраняется.

Объект этой проверки — модель данных и расчёт. Ответы API, права доступа, одновременные запросы и доставка сообщений проверяются на стенде по сценариям ниже.

## Подготовка к приёмке реализации

- Использовать согласованную версию API и тестовую базу; примеры запросов находятся в [Postman](../contracts/postman.collection.json).
- Проверки прав выполнять под отдельными учётными записями оператора и пользователя без права регистрации.
- Сбои доставки и сохранения воспроизводить на тестовом стенде совместно с разработкой. Проверять ответ, количество записей и журнал обработки.
- Значения времени 30 минут и 5 минут взяты из NFR-01 и NFR-04; они входят в условия проверки.

## Справочники и регистрация сбора

| Сценарий и требования | Исходные условия | Действия | Ожидаемый результат |
|:---|:---|:---|:---|
| **AC-01 · Найти согласованный сорт** (BR-01, FR-01) | Складской код `WMS-V-22` сопоставлен с сортом `VAR-017`. | Запросить сорт по этому коду, затем по неизвестному коду. | Известный код: `200`, сорт `VAR-017`. Неизвестный: `404 MAPPING_NOT_FOUND`, новый сорт не создаётся. |
| **AC-02 · Проверить сорт участка** (FR-01, CON-01) | Для участка `PLOT-044` и сезона 2026 указан сорт `VAR-017`. | Зарегистрировать сбор сорта `VAR-099` с этого участка. | `422 INVALID_REFERENCE`. Партия и сообщение не созданы. |
| **AC-03 · Не задвоить документ** (BR-02, FR-02) | Подготовлены два запроса на одну строку документа, с разными ключами запроса. | Отправить запросы одновременно. | Один ответ `201`, второй — `409 SOURCE_RECORD_EXISTS`. В базе одна партия. |
| **AC-04 · Восстановить потерянный ответ** (FR-02) | Регистрация завершилась, но клиент не получил ответ. | Повторить запрос с тем же ключом и данными, переставив поля JSON. | Возвращаются прежние `201`, номер партии и тело ответа. Второй партии и второго сообщения нет. |
| **AC-05 · Отклонить изменение при повторе** (FR-02) | Сбор зарегистрирован. | Повторить запрос с прежним ключом, изменив массу. | `409 IDEMPOTENCY_CONFLICT`. Исходная масса сохранена. |
| **AC-06 · Не сохранить часть операции** (FR-03) | Доступен стенд, на котором можно прервать транзакцию регистрации. | Вызвать сбой до завершения сохранения, проверить базу и повторить запрос. | После сбоя нет партии и сообщения. Повтор создаёт одну партию и одно сообщение. |
| **AC-13 · Проверить права** (NFR-02) | Есть действующий пользователь без права регистрации. | Отправить запрос без токена, с неверной подписью токена и от этого пользователя. | Соответственно `401`, `401`, `403`. Сбор не зарегистрирован. |
| **AC-18 · Проверить вводимые значения** (FR-01) | Остальные поля запроса заполнены корректно. | Поочерёдно передать нулевую и отрицательную массу, будущую дату, неверный сезон и поле неверного формата. | Значения, нарушающие бизнес-правила: `422 INVALID_BUSINESS_VALUE`. Ошибка формата: `400`. Партия не создана. |
| **AC-19 · Согласовать код сорта** (BR-01, FR-06) | В реестре есть новый код и код, уже связанный с сортом. | Подготовить выпуск для нового кода; затем попытаться переназначить существующий код другому сорту. | Новая связь содержит автора, основание и согласование владельца. Переназначение ожидает проверки исторических записей. |

## Передача данных и складская приёмка

| Сценарий и требования | Исходные условия | Действия | Ожидаемый результат |
|:---|:---|:---|:---|
| **AC-07 · Зарегистрировать сбор при недоступном складе** (FR-03, NFR-01) | WMS отключена на 30 минут. | Зарегистрировать несколько сборов, восстановить WMS и обработать сообщения. | Регистрация работает во время отключения. После восстановления — одна ожидаемая приёмка на каждую партию. |
| **AC-08 · Повторно отправить сообщение** (FR-03, NFR-01) | RabbitMQ принял сообщение, отметка публикации ещё не сохранена в базе отправителя. | Остановить и перезапустить отправителя. | Повтор использует прежний `eventId`. WMS не создаёт вторую ожидаемую приёмку. |
| **AC-09 · Сохранить два измерения** (BR-03, FR-04) | Производственная партия зарегистрирована с массой 8420 кг. | Передать приёмку 8370 кг и повторить то же сообщение. | Одна приёмка: 8370 кг. Сбор: 8420 кг. Разница: −50 кг. |
| **AC-10 · Восстановить обработку у получателя** (FR-04, NFR-01) | Получатель сохранил складские сведения, но ещё не подтвердил обработку. | Остановить получателя, затем возобновить доставку. | Повтор распознан по журналу сообщений. Вторая приёмка не создана. |
| **AC-14 · Проследить обработку партии** (NFR-03) | Сбор зарегистрирован, приёмка подтверждена. | Найти запрос регистрации и оба сообщения в журнале. | Единый `correlationId` связывает действия. Токен доступа в журнале отсутствует. |
| **AC-16 · Получить сообщения в обратном порядке** (FR-04, NFR-01) | У получателя отчётности ещё нет данных о партии. | Доставить сначала приёмку, затем сообщение о сборе. | Приёмка сохранена в ожидании связи; после получения сбора документы связаны. Данные не потеряны. |
| **AC-17 · Выделить необработанное сообщение** (FR-03, NFR-01) | Получатель возвращает временную ошибку. | Сохранить ошибку на протяжении трёх повторных попыток. | Сообщение перенесено в очередь ошибок с причиной и числом попыток. Исходная доставка подтверждена после успешного переноса. |

## Фиксация результата

По каждой проверке фиксируются ID сценария, версия требований и API, фактический результат и статус: пройдено, не пройдено или заблокировано. Подтверждение — ответ API, запись в базе, журнал сообщения или снимок отчёта. Для отклонения указываются шаг воспроизведения и номер дефекта.

При повторной регистрации и доставке обязательно проверяется количество созданных записей. Ответ об успехе сам по себе не подтверждает отсутствие дублей.

[Проверки файлов и примеров](../README.md#checks) выполняются до испытаний на стенде. Они проверяют согласованность материалов, а фактическое поведение реализации проверяется по сценариям выше.
