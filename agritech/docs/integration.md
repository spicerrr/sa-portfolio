# 🔌 контракты и доставка

## Граница синхронного и асинхронного

| Взаимодействие | Контракт | Подтверждение |
|:---|:---|:---|
| Разрешить исходный сорт | `GET /api/v1/source-mappings/resolve` | MDM вернул утверждённый ID |
| Зарегистрировать сбор | `POST /api/v1/harvest-batches` | Production зафиксировал факт и outbox |
| Прочитать партию | `GET /api/v1/harvest-batches/{batchId}` | Локальный факт и последняя проекция приёмки |
| Сообщить о регистрации | `harvest.batch.registered.v1` | Publisher confirm означает принятие брокером |
| Сообщить о приёмке | `warehouse.lot.received.v1` | Бизнес-факт опубликован WMS; consumer ack означает обработку конкретным потребителем |

Один OpenAPI-документ объединяет две области: путь mappings относится к MDM, пути harvest — к Production. Реальные URL задаются на уровне path servers. Демонстрационные имена `.example` не являются работающими адресами.

## Маршрутизация RabbitMQ

Exchange `agri.events` типа topic, durable. События persistent; рабочие очереди durable quorum. `eventType` — базовый тип, `eventVersion` — major-версия; routing key складывается как `eventType + '.v' + eventVersion`.

| Routing key | Рабочие очереди |
|:---|:---|
| `harvest.batch.registered.v1` | `wms.harvest.v1`, `bi.harvest.v1` |
| `warehouse.lot.received.v1` | `production.receipts.v1`, `bi.receipts.v1` |

Отдельная очередь на каждого независимого подписчика: общая очередь с несколькими consumers распределяла бы работу между ними, а не доставляла копию каждому.

## Гарантии

Production сохраняет партию и outbox в одной PostgreSQL-транзакции. Издатель повторяет неподтверждённые публикации с тем же `eventId`; ставит `published_at` после confirm и отсутствия mandatory return. При разрыве между confirm и отметкой возможен дубль.

WMS сохраняет ожидаемую приёмку вместе с inbox. При подтверждении кладовщиком WMS атомарно сохраняет складской факт и свой outbox. Consumer подтверждает сообщение только после commit обработки и inbox. Ключ inbox — `(consumer, eventId)`; бизнес-уникальность — `batchId` для полной приёмки. Это доставка как минимум один раз с идемпотентным эффектом, без заявления end-to-end exactly-once.

Для каждого рабочего consumer: 3 отложенные повторные попытки через 30 с, 2 мин, 10 мин; счётчик фиксируется при подтверждённом переносе в собственную retry-очередь. После третьего неуспеха — DLQ. Исходное сообщение ack только после подтверждения переноса. Временная ошибка БД — retry; несовместимая версия или невалидное тело — сразу DLQ. DLQ — очередь разбора, не автоматическое исправление. Возврат из DLQ сохраняет `eventId` и журналирует причину.

## Порядок и расхождения

Между двумя очередями BI порядок не гарантирован. Если приёмка пришла раньше партии, BI сохраняет её в отложенное хранилище по `batchId`, подтверждает сохранение и связывает после появления партии; повторный сбой связывания виден в сверке. В локальную таблицу с FK вставка выполняется только после существования партии. Это проектное требование; код такого потребителя не реализован.

`receivedWeightKg` может быть больше `weightKg`: в v1 это расхождение измерений, а не причина уничтожить факт. В отчёте выводится подписанная разница; порог допустимости требует согласования с бизнесом. Дата приёмки не раньше даты сбора проверяется после получения обоих фактов.

## Совместимость

Дополнительные необязательные поля совместимы в v1, consumers игнорируют неизвестные поля. Удаление поля, смена типа или смысла — новая major-версия и новая routing key. UTC timestamps в RFC 3339. JSON Schema описывает каждую ветку события отдельно; оба события сохраняют `correlationId` исходной регистрации.

## API-ошибки

| HTTP | code | Условие |
|:---|:---|:---|
| 400 | INVALID_REQUEST | Некорректный JSON, формат либо обязательный заголовок |
| 401 | UNAUTHENTICATED | Токен отсутствует, истёк или не проходит проверку |
| 403 | FORBIDDEN | Нет права на операцию |
| 404 | MAPPING_NOT_FOUND / BATCH_NOT_FOUND | Ресурс не найден |
| 409 | IDEMPOTENCY_CONFLICT / SOURCE_RECORD_EXISTS | Конфликт ключа/содержимого либо повтор исходного факта |
| 422 | INVALID_REFERENCE / INVALID_BUSINESS_VALUE | Сорт/участок несовместимы, масса/дата недопустимы |
| 503 | TEMPORARILY_UNAVAILABLE | Production или локальная БД недоступны; повтор с тем же ключом |

Ссылки на основы решения: [RabbitMQ reliability](https://www.rabbitmq.com/docs/reliability), [confirms](https://www.rabbitmq.com/docs/confirms), [OpenAPI 3.0.3](https://spec.openapis.org/oas/v3.0.3). Число попыток, сроки и состав очередей — решения кейса, не требования этих спецификаций.
