# 📦 переход исходных данных

Цель перехода — сохранить доказуемую связь исходной строки с целевым фактом. Старые строки не следует отправлять в Production API без проверки: повтор выгрузки и исправленный документ могут выглядеть как новые сборы.

## Промежуточный слой

| Запись | Ключ | Что сохраняется |
|:---|:---|:---|
| Снимок источника | `snapshot_id` | Источник, дата извлечения, файл, контрольная сумма |
| Исходная строка | `snapshot_id + row_locator` | Полное тело, документный ключ, масса и единица без изменений |
| Решение загрузки | Исходная строка | Статус, причина, нормализованное значение, согласующий |
| Реестр идентичности | `sourceSystem + sourceRecordId` | Полный исходный ключ, хеш значимых полей, целевой `batchId` после регистрации |
| Связь истории | Полные ключи сбора и приёмки | Основание, автор, дата; несколько кандидатов остаются неразрешёнными |

Промежуточный слой относится к загрузке / сверке; его таблицы не разделяются между Production и WMS как общая операционная БД. [DDL](../sql/00_legacy_staging.sql) сохраняет исходные строки и решения; применение в промышленной среде требует правил доступа и хранения.

## Правила преобразования

1. Зафиксировать неизменяемый снимок и контрольную сумму. Исходные значения не исправлять на месте.
2. Построить локальный ключ из области нумерации, документа и строки. Для примера `LEGACY + 2026/СБ-1284/1`.
3. Нормализовать массу только при явной единице (`т` → кг, `кг` → кг). Пустая / неизвестная единица блокирует запись.
4. Разрешить сорт только по утверждённому ключу; код участка — по согласованному реестру участков. Таблица сортов не используется для сопоставления участка.
5. Сравнить значимое тело с ранее принятым ключом. Идентичный повтор → `DUPLICATE`; другой состав полей → `CONFLICT`; неизвестная ссылка → `UNRESOLVED`.
6. Применить проверки UC-02. Для допустимой строки назначить `READY`; API всё равно выполняет собственные проверки и защищает уникальность.
7. До загрузки связать исторические приёмки только по подтверждённому документному отношению. При отсутствии отношения сохранить исключение; не вычислять связь по ближайшей массе.

Решение `READY` разрешает последующий импорт, но не означает наличие партии в Production. Скрипт [check_legacy.py](../scripts/check_legacy.py) проверяет только ключ, массу / единицу, сорт и повтор; он не выполняет загрузку, проверку посадок или историческую связь WMS.

## Контрольный набор

[legacy-harvest.csv](../examples/legacy-harvest.csv): пять строк — одна допустимая, её идентичный повтор, изменённая масса с тем же ключом, неизвестный сорт и масса без единицы. Ожидаются `READY / DUPLICATE / CONFLICT / UNRESOLVED / INVALID_UNIT`. В целевой контур может перейти только первая строка после проверки посадок и даты.

## Сверка и переключение

| Проверка | Ожидаемый результат | Кто подтверждает |
|:---|:---|:---|
| Число строк | Все исходные строки распределены между решениями; ни одна не исчезла | BI / производственный учёт |
| Масса | Сравнивать сумму принятых уникальных записей в кг; исключения отдельно | Производство |
| Связность | Каждый допущенный сорт и участок разрешён; истории без подтверждения не связаны | НСИ / агроном |
| Контроль приёмки | Складская масса хранится отдельно; есть список несопоставленных документов | Склад |
| Повтор загрузки | Новых фактов нет при неизменном наборе | Разработка / BI |

Перед переключением фиксируется момент закрытия старого журнала и список документов, принятых до него. Один документ не вводится одновременно по старому и новому пути. При откате опубликованные факты не удаляются: дальнейший ввод останавливается, журнал исходных ключей сохраняется для повторного запуска. Старый журнал остаётся доступен для чтения по согласованному сроку.
